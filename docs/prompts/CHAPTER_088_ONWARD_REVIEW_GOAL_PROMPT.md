最终目标是得到忠实、完整、术语稳定、中文自然、结构清楚、适合连续阅读的唯一中文正文，同时保留逐章可恢复、可审查的修改记录。

## 4. 已确认的翻译政策

### 4.1 玩家名、论坛名和账号名

- 不再默认使用英文或罗马字目标名。
- 人名型名称使用稳定的中文音译；有明确语义的账号名使用自然的中文意译。
- 同一源名全书只能有一个常规中文显示名；昵称、故意错拼名和被占用后的替代 ID 必须分别建条目。
- `ウェイン` 使用“韦恩”，`ヨーイチ` 使用“洋一”，`ギル` 使用“吉尔”，`ギルガメッシュ` 使用“吉尔伽美什”。
- `ギノレガメッシュ` 是不同的实际 ID，必须与“吉尔伽美什”区分；候选中文名为“吉诺雷伽美什”。
- `ジーンズ` 等语义型账号采用经确认的中文显示名，不得在同一人物后续出场时漂移回英文。
- 对尚无确认译名的账号，只能根据原文语义、既有出场和角色身份提出候选；不得批量猜音。存在多种合理译法时停止并询问用户。

### 4.2 固定术语

- `哲学者の卵`：`贤者之卵`。
- `大いなる業`：`伟大业障`。
- 同一个日文技能名必须映射到同一个中文技能名。不得为了句子变化，把同一技能临时写成多个名称。
- 当前既有技能默认继续使用已经确认的统一名，例如 `フレアアロー＝烈焰箭`、`サンダーボルト＝雷霆`、`エアカッター＝风之刃`；若原文实际是不同技能，按源词分别建条目，禁止按中文相似度合并。
- `アダマン` 家族按完整源词和上下文分层：生物系列使用“阿达曼”词干；明确的 `アダマンタイト` 和 `アダマンチウム` 作为不同材料；角色自己也不确定具体材料时，译文必须保留这种不确定性。
- 任何术语替换都必须有同段日文源词作为 guard，并使用最长源词优先，避免误伤包含相同片段的其他名字。

### 4.3 信息与叙事

- 严格保留否定、数量、百分比、单位、枚举对象和比较方向。
- 严格保留 `可能／大概／似乎／是否` 等不确定性，不得改成确定事实。
- 不得擅自切换第一、第三人称，不得改变动作执行者、发言人或指代对象。
- 不得提前解释伏笔、替角色增加动机、增加原文不存在的事件或世界观结论。
- 允许为了中文流畅调整语序、拆并短句、补最少量连接词；只要不增加事实、不删除有效信息、不改变角色语气。
- 人工稿中的增删若只改善中文节奏且不改变信息，可以保留；若与原文事实冲突，以原文为准并在审计记录中说明。

### 4.4 标点与正文格式

- 人物对话：`“……”`。
- 对话内引用：`‘……’`。
- 技能名：`〈……〉`。
- 系统、UI、世界公告：`**《……》**`，仅在原文确实属于这类内容时使用。
- 中文正文不得残留日式 `「」`、`『』` 或把所有 `《》` 机械当成技能。
- 标题和正文之间保持一致的 Markdown 层级；不得把作者后记、论坛帖或系统消息混成普通叙事段落。

### 4.5 删除规则

从面向阅读的正文中删除：

- 章节开头的投稿日期；
- “标题改订”“标题修改”等站点修订说明；
- 与故事无关的平台包装、求收藏、求评分文字；
- 经结构确认的作者后记、下章预告和发布说明。

不得删除：

- 剧情中的日期、时间、倒计时或年代；
- 角色在正文里阅读到的公告、论坛时间或系统时间；
- 虽像说明文字但实际包含设定、伏笔或剧情事实的正文。

被排除的内容不改写 `input_jp/`，只在中文阅读输出中隐藏，并在逐章审计记录中记为 `metadata_removed` 或 `afterword_excluded`。

## 5. 固定的逐章循环

严格一次处理一章。当前章全部验收通过后，才能进入下一章。

### Step A：定位与建立恢复点

1. 用章号唯一定位日文源文件和当前中文章节块。
2. 记录源文件、中文章节块和命中术语子集的哈希。
3. 解析标题、正文、系统/UI、论坛/聊天、分隔线、作者后记等结构。
4. 建立段落到稳定 `segment_id` 的对应关系。合段、拆段、重复段或插删导致歧义时，进入人工对齐队列。

### Step B：逐段对照

按原文顺序检查：

1. 是否漏译、多译或错位；
2. 否定、数字、单位、比较、枚举和不确定性是否完整；
3. 人名、论坛名、技能、物种、物品、地点是否符合当前确认词库；
4. 人称、性别代词、发言人和动作主体是否正确；
5. 中文是否存在机翻腔、拗口语序、重复表达或不自然直译；
6. 是否残留日文、乱码、错误括号或错误 Markdown；
7. 是否把原文暧昧内容过度解释，或把人工润色误当成错误。

### Step C：直接修正当前章

- 只替换已经唯一定位的当前章节块，不重写整本文件。
- 在不改变信息的前提下，把生硬译文润色为自然中文。
- 可直接修正有原文证据的错误；无需只生成建议而不落地。
- 不确定的语义、角色名或术语不得擅自决定，记录后停止当前章。
- 不得改写任何 `input_jp/`、导入的人工稿、`human_approved_final` 或 legacy baseline。

### Step D：本章复查

修改后重新对照原文，并运行本章范围的定向检查：

- 章节和 segment 覆盖完整，无漏段、重段或错位；
- 修改前后结构边界一致，除明确排除的元数据和后记；
- 术语和角色名没有旧变体；
- 同一日文技能名的中文名一致；
- 无日文残留、乱码、错误引号和错误系统消息样式；
- 数字、单位、否定、模态、人称和指代再次核对；
- 对本章修正规则再运行一次，第二次应为零新增变更。

### Step E：记录并推进

每章完成后，在忽略的本地进度账本中原子记录：

- `chapter_id`、源路径和中文章节锚点；
- 修改前后哈希；
- 原文段落数、中文段落数；
- 论坛楼层数、引用数或其他特殊块计数；
- 修改数及 `MISTRANSLATION / OMISSION / INCONSISTENT_TERM / FORMAT / METADATA` 分类；
- 未决问题、验收结果、状态、下一章号。

状态只能是 `in_progress / needs_review / complete / blocked`。恢复时从第一个非 `complete` 章节开始，不得只凭“上次打开了哪一章”推断进度。

## 6. 第 88 章专属处理

第 88 章包含一段完整论坛讨论，不能把它排成普通叙事文本。

已知结构基线：

- 论坛块位于两处 `＊＊＊` 分隔之间；
- 一个线程标题；
- 楼层从 1 到 57，连续且不得缺号、重号或改序；
- 共 21 处 `>>N` 引用，全部指向此前已有楼层；
- 1 楼用户名为 `ウェイン`，可据此显示“楼主”，但原文没有独立 OP 标签；
- 论坛结束后恢复小说正文；
- 后部 `---` 是作者后记分界，不是系统消息。

中文阅读版使用以下格式：

```markdown
---

### 【玩家论坛】线程标题

> 注：以下为游戏内玩家论坛讨论。楼层依原文编号；“回复 N 楼”表示引用对应楼层。

**第 1 楼｜韦恩（楼主）**

发言正文。

**第 2 楼｜中文用户名**

> 回复 1 楼

发言正文。

……

### 【论坛讨论结束】

---
```

执行要求：

1. 所有用户名按全书确认后的中文映射显示；不得在本章临时发明另一套译名。
2. 只在第 1 楼标一次“楼主”。不得新增头像、时间、管理员、系统账号或原文不存在的多层线程。
3. 每个 `>>N` 转成独立的 `> 回复 N 楼`；必须同时在审计数据中保留 `reply_to=N` 或原始 `>>N`，确保可逆。
4. 引用只能指向已出现楼层；论坛块完成后必须验证 `floor_count=57`、`reply_count=21`。
5. 论坛说明只出现一次。它是阅读辅助注释，不得伪装成原文或系统通知。
6. 论坛后恢复普通小说标点和段落；作者后记按删除规则从阅读正文排除。

## 8. 必须停止并询问用户的情况

- 源章或目标章缺失、重复；
- 章节块或 segment 无法唯一对齐；
- 合段、拆段、插删或重复文本导致多种合理映射；
- 原文存在两种合理解释，会影响人物、事件、伏笔或世界观；
- 新中文名或术语存在多种合理形式，且当前词库没有已确认答案；
- 修改将冲突或覆盖人工锁定内容；
- 论坛楼层、引用目标或发言人归属无法恢复；
- workspace baseline 校验出现 drift 或错误；
- 需要真实 API、发布、Git、删除数据或其他未授权外部效果；
- 出现 P0/P1 问题。
